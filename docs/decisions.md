# Decisions

Beacon follows its specification and departs from it in the places below, each with the reason. What is not built yet, and what nothing has verified on a device, is listed at the end.

## Where the implementation departs from the specification

| Specification                                                        | Implementation                                                                                                                                                                                                                                         | Why                                                                                                                                                                                              |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `releaseRoute` with `selection.target` or `selection.newer`          | `targetRoute` and `newerRoute`: the mode is the factory                                                                                                                                                                                                | Each mode has different options (`newerRoute` needs a version strategy and the running order), and a union of options would need runtime checks.                                                 |
| A separate versions package                                          | `@priemskiyyy/beacon/versions` (`semver`, `integer`, `custom`)                                                                                                                                                                                         | One fewer package to version, with no dependency to justify a split. Prerelease admission is an option of `semver`, not of selection.                                                            |
| Several reference kinds, and one for waiting and one for activation  | Two references, `offer` and `prepared`, minted by the core; a command declares `offer`, `prepared`, `optional-offer` or `none`                                                                                                                         | A waiting worker is an offer of the service worker route, and an activated one is its prepared target. Fewer kinds, the same guarantees.                                                         |
| A source can answer unavailable or not modified                      | `read` resolves a `SourceRead` or rejects; the HTTP adapter keeps the validator and the last document, and its client answers `changed` or `not-modified`                                                                                              | A missing answer is never "no release". Conditional requests belong to the transport that understands them.                                                                                      |
| The HTTP adapter parses a standard manifest                          | `http({ request })` takes the application's client call, which resolves a typed `HttpAnswer`; `readStandardManifest` and `parseStandardManifest` are the optional standard schema and parser, and the types follow the routes the application declares | Validation stays with the client the application already has, and the standard schema is one client among others. It rejects a manifest whole or accepts it whole, with no transport of its own. |
| Drivers may write running facts                                      | Running facts come from readers passed to `Beacon`; a driver receives a read-only view and cannot write them                                                                                                                                           | Duplicate authority for what is running is impossible by structure.                                                                                                                              |
| Several ways to register a blocker                                   | Only `disruptions.register(participant)`; a blocker is a participant that blocks                                                                                                                                                                       | One mechanism to reason about and test.                                                                                                                                                          |
| `startUpdate({ flow })` for Google Play                              | `startFlexibleUpdate` and `startImmediateUpdate`, and `completeUpdate`                                                                                                                                                                                 | Impacts are declared per command, so a participant is asked only about what a flow does, and a flow Play does not allow is refused by the offer.                                                 |
| `createReleaseDriver` returns a driver                               | It returns the driver route, `{ kind: "driver", driver }`, which goes into `routes` as it is                                                                                                                                                           | A driver is never used except as a route.                                                                                                                                                        |
| A native handle may be anything                                      | `TNative extends object`                                                                                                                                                                                                                               | `route.native` is `null` while no session is open, so a handle that could be `null` would be ambiguous. A type error says so.                                                                    |
| A command may be named anything                                      | A command cannot be named `state`, `native`, `capabilities`, `check` or `acknowledge`, and its parameters cannot be named `offer`, `prepared` or `signal`                                                                                              | The route handle is the command facade plus its own members, and a collision would silently overload one of them. The types refuse it.                                                           |
| `replaceScope(next)` returns a blocked result, or replaces the scope | `beacon.replaceScope(next)` answers `replaced`, `unchanged` or `blocked` with the route whose operation is running or unresolved, and forgets everything the old scope taught                                                                          | The underlying work cannot be given to another scope, and running facts are never rewritten. A blocked replacement leaves the old scope entirely in force.                                       |
| One driver per updater, checked in development                       | A driver names the native manager it holds with `exclusive`, and a second session that would open the same manager fails to open with `DRIVER_FAILED`                                                                                                  | The Play bridge and the Expo module cannot be raced from two Beacons, and the failure is visible instead of silent.                                                                              |
| A TestFlight build gets no App Store route automatically             | `appStoreLookup` answers a decision of no release, reason `other-distribution`, for a scope whose distribution is not `app-store`, and makes no request                                                                                                | The distribution is the application's configuration, and the store is asked only about the store's own builds.                                                                                   |
| A journal for every disruptive command                               | An intent is written, in `best-effort` or `required` mode over an injected `JournalStorage`, only before a command that replaces the realm; `reportReady` is kept in memory                                                                            | Only a reload or restart has a next boot to read the intent back. A required write that fails stops the command, and a readiness report needs no storage to be true.                             |
| An accepted reload releases its reservations                         | A command that replaces the realm (`document-replacement`, `javascript-restart`) leaves its route unresolved and keeps its reservations until `route.acknowledge()`                                                                                    | The old realm may stay alive, and participants must not resume as if nothing was requested. Acknowledging is the application's explicit choice.                                                  |
| A caller's abort after a dispatch                                    | The command is `indeterminate` with reason `aborted-after-dispatch`, and a later provider result still releases or holds the route as it reports                                                                                                       | An abort ends a wait. It is never proof the provider stopped.                                                                                                                                    |
| A test clock and a system clock                                      | `BeaconClock` has `now`, `monotonic` and `setTimer`; only `createSystemClock` reads the host                                                                                                                                                           | Lint forbids every other time and timer source, so tests and suspension are controlled from one place.                                                                                           |

## Not built yet

Each item is a specified feature, not a decision to omit it.

- **Dismissals** (`POL-12`): a dismissal never changes support, and none is stored yet. The presentation layer is headless and not built.
- **Automation gated by the journal's budget**: the journal counts boots that left a target unreached and says when the budget is spent, but nothing gates a command on it, since no scheduler exists to automate one.
- **Unattributed change**: a release change observed at boot without a journal record is not reported as such, since Beacon does not keep the last boot's identities apart from intents.
- **`beacon.reconcile()`**: drivers reconcile once when a session opens, and again when a scope is replaced.
- **Scheduler and triggers**, retries and backoff.
- **Workbox profile** and the service worker identity handshake. The service worker route reports an update as ready with an unknown build.
- **Expo hook bridge**: the Expo route is the command profile, and autonomous native startup checks are not observed.
- **Other framework bindings**, devtools, the documentation site, runnable examples, and the ecosystem bridges to Silo, Pulse, Reach, Porter, Flare and Simulcast.
- **Cross-tab coordination** for service workers: activation is a takeover of every tab of the scope, and one tab's guard cannot certify the others.
- **Optional signatures** on manifests, and the rejection of duplicate JSON keys in the standard manifest, whose decoder keeps the last key.
- **Retry hints**: a `429` fails the read and `Retry-After` is not honoured, since no scheduler owns a retry budget.
- **Reload recovery** for a stale chunk and page-restoration (BFCache) handling in the browser adapter.

## Not verified on a device

Everything is tested in process against fakes, and the Expo and React Native adapters are also typechecked against their real SDK types. Nothing has run in a real browser, on a device, or against a real Play or App Store distribution. Before a stable release of an adapter, run it once by hand in a real application on each platform it maps, and say what you ran.
