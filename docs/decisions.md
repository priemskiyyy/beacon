# Decisions

Beacon follows its specification and departs from it in the places below, each with the reason. What is not built yet, and what nothing has verified on a device, is listed at the end.

## Where the implementation departs from the specification

| Specification                                                                                  | Implementation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Why                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `releaseRoute` with `selection.target` or `selection.newer`                                    | `targetRoute` and `newerRoute`: the mode is the factory                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Each mode has different options (`newerRoute` needs a version strategy and the running order), and a union of options would need runtime checks.                                                                                                                                                                                                                                                                                |
| A separate versions package                                                                    | `@priemskiyyy/beacon/versions` (`semver`, `integer`, `custom`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | One fewer package to version, with no dependency to justify a split. Prerelease admission is an option of `semver`, not of selection.                                                                                                                                                                                                                                                                                           |
| Several reference kinds, and one for waiting and one for activation                            | Two references, `offer` and `prepared`, minted by the core; a command declares `offer`, `prepared`, `optional-offer` or `none`                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | A waiting worker is an offer of the service worker route, and an activated one is its prepared target. Fewer kinds, the same guarantees.                                                                                                                                                                                                                                                                                        |
| A source can answer unavailable or not modified                                                | `read` resolves a `SourceRead` or rejects; the HTTP adapter keeps the validator and the last document, and its client answers `changed` or `not-modified`                                                                                                                                                                                                                                                                                                                                                                                                                                                    | A missing answer is never "no release". Conditional requests belong to the transport that understands them.                                                                                                                                                                                                                                                                                                                     |
| The HTTP adapter parses a standard manifest                                                    | `http({ fetch })` takes the application's client call, which resolves the typed `HttpAnswer`; `readStandardManifest` and `parseStandardManifest` are the optional standard schema and parser, `standardManifestSource({ url, routes })` is the one call that asks the global `fetch` for a manifest at a URL, and the types follow the routes the application declares                                                                                                                                                                                                                                       | Validation stays with the client the application already has, and the standard schema is one client among others. It rejects a manifest whole or accepts it whole. `http` has no transport of its own, and the one request the package makes is the source over a URL, whose client is injectable.                                                                                                                              |
| The standard manifest requires its scope, its times, its revision and a known identity in full | `schemaVersion` and `routes` are required; `application`, `environment`, `platform`, `distribution`, `issuedAt`, `expiresAt` and `decisionRevision` are optional and judged whenever present, and a release's `identity` may be a text, which is known under `scope.application` and the domain its route declares (`web-artifact` for a `target` route, none for a `candidate`). An absent `expiresAt` is evidence that holds for the client's window, `lifetime` from the read on the Beacon's clock, and a read the server confirms starts it again; an absent `issuedAt` skips the order and skew checks | A static host cannot write times, a revision or a scope it does not know, and a newcomer's first manifest was 17 leaves with 12 constants. The absence is never read as a claim: the window is named the client's, an unnumbered manifest cannot tell an older copy from a newer one, which the documentation says beside the freshness headers that bound it, and a manifest that does state them is judged exactly as before. |
| Drivers may write running facts                                                                | Running facts come from local readers passed to `Beacon`, one per subject; a driver receives a read-only view and cannot write them. A driver route may offer a default reader for its own subject, used only when the application passes none                                                                                                                                                                                                                                                                                                                                                               | There is still one authority per subject: the reader the application passes always wins, the default reads what the provider's own module says runs, and no driver ever writes a fact. A feed route whose subject has no reader cannot be built, since it could never offer anything.                                                                                                                                           |
| Several ways to register a blocker                                                             | Only `disruptions.register(participant)`; a blocker is a participant that blocks                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | One mechanism to reason about and test.                                                                                                                                                                                                                                                                                                                                                                                         |
| `startUpdate({ flow })` and `requestReload`, `activateWaiting`                                 | One shared vocabulary of verbs: `reload`, `activate`, `download`, `update` (Play's blocking flow), `restart` (Play's completion), `openStore`                                                                                                                                                                                                                                                                                                                                                                                                                                                                | A route method promises no more than its receipt does: `reload()` is answered with `reload-requested`, and an accepted call is a request, never an effect. Impacts are declared per command, so a participant is asked only about what a flow does, and a flow Play does not allow is refused by the offer.                                                                                                                     |
| `createReleaseDriver` returns a driver                                                         | It returns the driver route, `{ kind: "driver", driver }`, which goes into `routes` as it is                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | A driver is never used except as a route.                                                                                                                                                                                                                                                                                                                                                                                       |
| A native handle may be anything                                                                | `TNative extends object`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | `route.native` is `null` while no session is open, so a handle that could be `null` would be ambiguous. A type error says so.                                                                                                                                                                                                                                                                                                   |
| A command may be named anything                                                                | A command cannot be named `state`, `native`, `capabilities`, `check` or `acknowledge`, and its parameters cannot be named `offer`, `prepared` or `signal`                                                                                                                                                                                                                                                                                                                                                                                                                                                    | The route handle is the command facade plus its own members, and a collision would silently overload one of them. The types refuse it.                                                                                                                                                                                                                                                                                          |
| `replaceScope(next)` returns a blocked result, or replaces the scope                           | `beacon.replaceScope(next)` answers `replaced`, `unchanged` or `blocked` with the route whose operation is running or unresolved, and forgets everything the old scope taught                                                                                                                                                                                                                                                                                                                                                                                                                                | The underlying work cannot be given to another scope, and running facts are never rewritten. A blocked replacement leaves the old scope entirely in force.                                                                                                                                                                                                                                                                      |
| One driver per updater, checked in development                                                 | A driver names the native manager it holds with `exclusive`, and a second session that would open the same manager fails to open with `DRIVER_FAILED`                                                                                                                                                                                                                                                                                                                                                                                                                                                        | The Play bridge and the Expo module cannot be raced from two Beacons, and the failure is visible instead of silent.                                                                                                                                                                                                                                                                                                             |
| A TestFlight build gets no App Store route automatically                                       | `appStoreLookup` answers a decision of no release, reason `other-distribution`, for a scope whose distribution is not `app-store`, and makes no request; the handoff of the App Store and `playStore` of Google Play are unsupported with the same reason for a scope that is not their own (`app-store`, `google-play`), and open nothing                                                                                                                                                                                                                                                                   | The distribution is the application's configuration, and a store is asked, or opened, only for its own builds: a forced upgrade that names a store route must never send a sideloaded or development build to the wrong store. A mechanism learns the distribution from the scope its `open` is given.                                                                                                                          |
| A journal for every disruptive command                                                         | An intent is written, in `best-effort` or `required` mode over an injected `JournalStorage`, only before a command that replaces the realm; `reportReady` is kept in memory                                                                                                                                                                                                                                                                                                                                                                                                                                  | Only a reload or restart has a next boot to read the intent back. A required write that fails stops the command, and a readiness report needs no storage to be true.                                                                                                                                                                                                                                                            |
| An accepted reload releases its reservations                                                   | A command that replaces the realm (`document-replacement`, `javascript-restart`) leaves its route unresolved and keeps its reservations until `route.acknowledge()`                                                                                                                                                                                                                                                                                                                                                                                                                                          | The old realm may stay alive, and participants must not resume as if nothing was requested. Acknowledging is the application's explicit choice.                                                                                                                                                                                                                                                                                 |
| A reload the page cancels is reported by the adapter                                           | `browserReload` answers `accepted` and stops there; the application acknowledges a cancelled navigation, with a `beforeunload` handler that the documentation shows and a Chromium spec runs against real prompts                                                                                                                                                                                                                                                                                                                                                                                            | Nothing tells the page that the user stayed, so the only evidence is a timer that runs after the prompt closes, and only the application knows that it asked for a prompt. The adapter cannot tell a prompt from a navigation that is about to replace the document, and a release it made on that guess would reopen a draft the reload was about to destroy.                                                                  |
| A caller's abort after a dispatch                                                              | The command is `indeterminate` with reason `aborted-after-dispatch`, and a later provider result still releases or holds the route as it reports                                                                                                                                                                                                                                                                                                                                                                                                                                                             | An abort ends a wait. It is never proof the provider stopped.                                                                                                                                                                                                                                                                                                                                                                   |
| React hooks take a route handle                                                                | The hooks read a route by name from the Beacon that a provider publishes, and `Register` tells them which Beacon that is; a handle you hold is read with `useObservable(handle.state)`. The provider starts the session unless given `start={false}`                                                                                                                                                                                                                                                                                                                                                         | A name is checked against the routes the Beacon has and gives the state its route's own types, with no handle to pass around. Reading stays passive, and an application that forgot to start a session looked as if nothing happened. Every binding has the same shape.                                                                                                                                                         |
| Hydration reads what the server rendered                                                       | Every observable has `getInitial()`, its value before any session, and a binding renders that on the server and on the hydrating render                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | A session that starts between the server render and a late boundary's hydration cannot make the markup disagree.                                                                                                                                                                                                                                                                                                                |
| A check shares reads with the others in flight                                                 | One `check()` starts the read of every route and of the policy in the same turn, after waiting once for the running facts it needs (every configured one when there is a support policy)                                                                                                                                                                                                                                                                                                                                                                                                                     | A source that answers at once is still read once for one check, however quickly it answers.                                                                                                                                                                                                                                                                                                                                     |
| Adapters name the SDK versions they support                                                    | The SDK peers of the adapters are open ended from the oldest release whose declarations the adapter's structural type fits, and `scripts/verify-peers.mjs` installs that floor and the newest release it was run against outside the workspace and typechecks them                                                                                                                                                                                                                                                                                                                                           | An adapter imports no SDK, so only declarations can disagree, and a cap would turn a structural fit into an `ERESOLVE` on the next release. It proves types and never a runtime: what an older SDK does when called is not verified.                                                                                                                                                                                            |
| A test clock and a system clock                                                                | `BeaconClock` has `now` and `setTimer`; only `createSystemClock` reads the host                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Lint forbids every other time and timer source, so tests and suspension are controlled from one place.                                                                                                                                                                                                                                                                                                                          |

## Not built yet

Each item is a specified feature or an adapter that was left out, not a decision to omit it, with the reason it is not there.

- **Dismissals** (`POL-12`): a dismissal never changes support, and none is stored yet. The presentation layer is headless and not built.
- **Automation gated by the journal's budget**: the journal counts boots that left a target unreached and says when the budget is spent, but nothing gates a command on it. [`@priemskiyyy/beacon-triggers`](triggers.md) only checks and never commands, so there is nothing automated to gate yet.
- **Unattributed change**: a release change observed at boot without a journal record is not reported as such, since Beacon does not keep the last boot's identities apart from intents.
- **`beacon.reconcile()`**: drivers reconcile once when a session opens, and again when a scope is replaced. A return to the foreground can only check, since the core has no call that asks a driver to reconcile again.
- **`Retry-After`**: a `429` fails the read and the header is not honoured, because a failed check keeps only a code and a message. The backoff of the triggers has no hint to read, and the HTTP adapter leaves retry policy to the application.
- **A relative expiry**: a source answers `expiresAt` as epoch milliseconds and never as a lifetime from the read, such as `max-age` or a TTL. A source that knows only a lifetime adds it to the time it read, as the Firebase source does with `maxAge`, and the core has no field that takes one.
- **Workbox profile** and the service worker identity handshake: the page and its worker cannot yet agree on which build the worker serves, so the service worker route reports an update as ready with an unknown build.
- **Cross-tab coordination** for service workers: activation is a takeover of every tab of the scope, and one tab's guard cannot certify the others.
- **Expo hook bridge**: the Expo route is the command profile, and autonomous native startup checks are not observed.
- **Adapters for a desktop or extension host and for Capacitor**: Electron, Tauri, browser extensions and Capacitor each have their own update channel and their own way to read the binary, and nothing in this repository can run one. `@priemskiyyy/beacon-native` reads React Native and Expo only.
- **Adapters for the other over-the-air updaters that work like CodePush**, such as `hot-updater` and Capawesome's live update: each has a JavaScript API of its own that nothing here was proved against, so the CodePush adapter maps only the family that shares Microsoft's.
- **The ecosystem bridges** to Silo, Switchboard, OpenFeature, Porter, Flare and Simulcast. An application can read each through a source or a policy of its own. A Pulse and a Reach condition are not on the list: the triggers take them as they are.
- **More than one registered Beacon** in one program: `Register` names one, and the hooks read that one. Any other Beacon is read with `useObservable(other.route("name").state)`.
- **Optional signatures** on manifests, and the rejection of duplicate JSON keys in the standard manifest, whose decoder keeps the last key.
- **Reload recovery** for a stale chunk and page-restoration (BFCache) handling in the browser adapter.

## Not verified on a device

Everything is tested in process against fakes, and the Expo, CodePush, Firebase Remote Config, native build and triggers packages are also typechecked against the real types of the SDKs they take. The example apps run in Chromium under Playwright, but against a scripted release lab, so they exercise the core and the React binding in a real browser and no adapter against a real provider. One more spec runs `browserStorage` and `webBuild` of the browser package in Chromium, with a real reload, a real quota, a sandboxed frame and a real Vite build; Safari, Firefox, private browsing and the eviction of site data are not run. Nothing has run on a device, or against a real Play or App Store distribution. The packages that ship to React Native also run on both Hermes builds that React Native ships and under a test renderer, in an environment where the globals Hermes lacks are removed; that is not a device. [React Native](react-native.md#what-no-device-has-run) lists what a device still has to show: an Expo update launched and read back through the journal, `reloadAsync` and the `AppState` listeners it ends, `AppState` transitions, what `@react-native-community/netinfo` reports on a real change of network, timers while the app is in the background, what `expo-application` reads in Expo Go and in a development build, the journal's storage under a kill, Play's flows through a real bridge, a CodePush package staged, restarted into and read back through the journal, `Linking.openURL` to the store, the native fetch and fetch time of Firebase Remote Config, `fetch` caching and redirects on iOS and Android, and Fast Refresh in Metro. Before a stable release of an adapter, run it once by hand in a real application on each platform it maps, and say what you ran.
